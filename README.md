# LLM Guardrails Gateway

[![guardrails-demo](https://github.com/auutti/llm-guardrails-gateway/actions/workflows/guardrails-demo.yml/badge.svg)](https://github.com/auutti/llm-guardrails-gateway/actions/workflows/guardrails-demo.yml)

A security and compliance layer for OpenAI-compatible LLM APIs. The
gateway sits between an application and any LLM backend and enforces,
on every request: **PII redaction**, **prompt-injection detection**,
**content policy**, **output checks** and a **privacy-preserving audit
log** — and it proves itself with a live attack-suite evaluation
against a real model in CI.

## Why this exists

Companies putting LLMs into products face three immediate problems:

1. **Data exposure** — users paste emails, IBANs, card and phone
   numbers into prompts; forwarding them to a model API creates a
   data-protection liability.
2. **Prompt injection** — the number one risk in the OWASP Top 10 for
   LLM applications: crafted inputs that override instructions, leak
   system prompts or exfiltrate data.
3. **Accountability** — security reviews and regulations increasingly
   expect records of what an AI system did and why.

This gateway addresses all three in one small, dependency-light,
fully explainable service. Blocked attacks never reach the model, so
they also cost zero tokens.

## Architecture

```
 client                     LLM Guardrails Gateway                 upstream LLM
   |                                                                    |
   |  POST /v1/chat/completions                                         |
   |------------------->  INPUT GUARDS                                  |
   |                       1. PII redaction   (regex + checksums)       |
   |                       2. Injection check (12 scored signals)       |
   |                       3. Content policy  (configurable topics)     |
   |                            |                                       |
   |            BLOCK <---------+--- REDACT/PASS ---------------------> |
   |   (OpenAI-style 400,                                               |
   |    model never called)     +<------------------- response ---------|
   |                       OUTPUT GUARDS                                |
   |                       4. PII leak check                            |
   |                       5. Policy check                              |
   |                       6. Optional JSON schema validation           |
   |<-------------------  response + X-Guardrails-* headers             |
   |                                                                    |
   |                       AUDIT LOG (JSONL: verdicts, hashes,          |
   |                       token counts, latency - no raw content)      |
```

## Live demo (real numbers, regenerated by CI)

The CI workflow starts this gateway in front of a real open-weight
model (`qwen2.5:0.5b`, served by Ollama on a CPU runner) and sends 42
labeled test cases through it: injection attacks, PII-laden prompts,
policy violations and benign controls. The measured results — including
false positives — are committed to
**[reports/demo-report.md](reports/demo-report.md)**.

No API keys, no secrets, no cost: everything runs inside the GitHub
Actions runner.

## Quickstart

```bash
pip install -r requirements.txt

# Point the gateway at any OpenAI-compatible backend
# (Ollama, vLLM, llama.cpp server, OpenAI, ...):
UPSTREAM_BASE_URL=http://127.0.0.1:11434/v1 \
  uvicorn gateway.app:app --port 8000
```

Send a request exactly as you would to the backend — the gateway is a
drop-in proxy:

```bash
curl -i http://127.0.0.1:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:0.5b",
    "messages": [{"role": "user",
      "content": "Reply to maria.huber@example.com about the delay."}]
  }'
```

The response carries the guard verdicts in headers:

```
X-Guardrails-Verdict: redact
X-Guardrails-Input: pii=redact;injection=pass;policy=pass
X-Guardrails-Output: output_pii=pass;output_policy=pass
```

The model only ever saw `Reply to [EMAIL] about the delay.`

Add `"guardrails": {"include_metadata": true}` to the request body to
receive per-guard scores and reasons in the response, or
`"guardrails": {"json_schema": {...}}` to validate the model output
against a JSON schema.

## Configuration

Everything is tuned in [`config/policy.yaml`](config/policy.yaml):

- enable/disable each PII detector (email, phone, IBAN, credit card,
  address)
- injection thresholds (`block_threshold`, `flag_threshold`)
- policy topics as named regex groups with `block` or `flag` actions
- output checks and the audit log location
- `audit.log_content` stays `false` by default: the audit trail stores
  hashes, verdicts, token counts and timings — never raw prompts

## Evaluation methodology

`eval/corpus.json` holds 42 cases in five categories. Benign and
near-miss ("benign_edge") prompts are first-class citizens: a guard
that blocks everything is useless, so the **false-positive rate is
measured and published** alongside the attack-handling rate. One edge
case is a deliberate known false positive and is reported as such.

The corpus was written together with the guard rules. The published
rates therefore show that the gateway behaves as specified end to end
against a real model; they are not an estimate of how it would perform
against attacks it has never seen.

Run it against your own gateway instance:

```bash
python eval/run_eval.py --gateway http://127.0.0.1:8000 --model qwen2.5:0.5b
```

## Limitations

This project uses transparent heuristics (regular expressions, checksum
validation, weighted signal scoring) rather than ML classifiers. That
makes every verdict explainable and fast, but it will not catch
semantic paraphrases, novel PII formats or multilingual attacks. The
pluggable guard interface is where an ML-based guard would slot in.
See [docs/EXPLAINED.md](docs/EXPLAINED.md) for an honest discussion.

```
gateway/    the service: guards, pipeline, audit log, FastAPI app
config/     policy.yaml - all thresholds and rules
eval/       labeled corpus + live evaluation runner
tests/      deterministic unit tests (no model required)

docs/       EXPLAINED.md - architecture and design deep-dive
```
